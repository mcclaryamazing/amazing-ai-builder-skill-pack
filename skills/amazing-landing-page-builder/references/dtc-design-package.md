# DTC Design Package

Use for full-page strategy, copy, wireframes and implementation handoff. For limited copy or audits, deliver only the requested scope. The package exists to help create and build the page, not to collect paperwork.

## Work From The Buying Decision

Read `conversion-copy.md` before drafting and `listicle-playbook.md` when using the recommended cold-traffic listicle. Use supplied materials as the working facts; the owner handles their accuracy and approval. There is no claim-verification phase, proof ledger or substantiation readiness score.

Start with the audience, existing desire, practical benefit and emotional why. Decide what the ad already established, what remains to be understood, why this product is worth choosing, and what action should follow. State inferred traffic or audience assumptions briefly. Use all supplied relevant material before asking for more; identify actual conflicts without reopening every product fact.

Default to Meta paid-social cold prospecting, a brand-owned long-form listicle, and a mobile-first layout. Use the archetype rules in `../SKILL.md` and `dtc-archetypes.md` when another route is appropriate. Develop reasons beyond benefit summaries. Length follows the useful argument; a shorter route needs a strategic rationale, not prior test data.

## Ask Only For A Decision You Need

Ask when the actual product, conversion goal, required offer choice, response path or a concrete conflict prevents useful progress. Use existing conversation context first. Missing optional reviews, certifications, guarantees or campaign data do not block a draft. Omit unspecified terms rather than creating placeholders. Shopify access is needed for implementation, not design.

Infer style, voice and audience emphasis from the supplied materials when possible, and note those assumptions internally. For new information beyond the brief, use requested research or a genuine source; do not invent specifics. Keep owner questions separate from the finished customer experience.

## Deliverable

Use Markdown, JSON or another maintainable format. Do not duplicate the same strategy across multiple mandatory schemas. Include:

1. **Conversion brief:** audience/desire, emotional payoff, product-specific big idea, why ownership matters without a promotion, traffic/ad continuity, format and response path. Explain any meaningful departure from the defaults; apply the existing PDP gate when relevant.
2. **Headline recommendation:** three distinct candidates, recommended H1 and short rationale. For listicles, the count and reason promise are in the main visible H1; include the compact distinct-reason map.
3. **Full page copy:** finished hero, introduction, sections/reasons, useful customer material, offer choices and CTAs, remaining buying questions and close. Keep sources/production notes outside copy unless a customer-facing citation belongs in the page.
4. **Offer and interaction:** named packages, current supplied contents/quantities/prices/terms, recommendation basis, CTA destinations and selection states. Proposed offer changes remain proposals until the owner accepts them.
5. **Visual system:** brand direction, typography, colors, whitespace and section rhythm, desktop/mobile behavior and exact image slots. Each image has a persuasive job and intended crop, size and alt text.
6. **Rendered wireframe:** full-copy desktop/mobile artifact, using the prescribed placeholders in every image slot before imagery approval.
7. **Review and handoff:** conversion findings/fixes, actual viewports and interactions inspected, image approval or explicit waiver of the pause, implementation notes if requested, and only owner decisions that still matter. Do not include fact-check lists.
8. **Metadata:** page-specific title, description and social preview direction for full designs/builds.

For multiple supplied ads, map materially different promises to distinct openings or pages as recommendations within scope; do not silently create extra pages or change campaigns. Keep available proof with the argument it strengthens rather than assembling mandatory proof stacks.

## Wireframe And Image Approval

Create an actual reviewable rendered page, not just a JSON spec. Use full copy and the exact image-placeholder format in SKILL.md. Define ideal images from the argument before selecting assets. Preserve aspect ratios, placement, crop behavior and responsive spacing. Existing assets can inform the product depiction; final selection/insertion waits until approval.

Review desktop and mobile hierarchy, typography, whitespace, image roles, reason depth, product/offer clarity and action. Apply `dtc-qa-rubric.md` and the independent final conversion review before delivering. Resolve accepted findings and recheck affected rendering. Explicit end-to-end authorization may waive the conversational image-approval pause, not internal review. After approval, select assets that fit the approved visual jobs.

## Ready To Build

The builder should be able to reproduce the approved page without inventing copy or redesigning the argument. Confirm that the H1 earns attention, the product and offer are clear, the reasons develop desire, the response path works in the design, the mobile reading experience is strong, image slots are precise and accepted editorial findings are fixed. Technical implementation and checkout verification follow in their own phase. A lack of third-party proof is not a design blocker.
